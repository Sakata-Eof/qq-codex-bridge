# 任务状态与诊断

任务时间线把一批输入从接收到结果投递串起来。QQ `/status` 和 `/context` 追加当前聊天最近任务的短编号、阶段、执行状态和投递状态；本机历史页展开“账号最近任务”查看最近任务及阶段详情。编号可用于对应两处记录。

## 怎么理解状态

| 所处阶段 | 含义 |
| --- | --- |
| 已接收、等待合并消息 | 收到普通输入，正在等待邻近的文字或附件 |
| 等待处理、准备附件、启动任务 | 排队、媒体准备或启动请求尚未完成 |
| 执行中、等待审批、等待回答 | 模型正在执行，或需要当前账号作出选择 |
| 已补充到当前任务 | 补充批次已被接收，关联到原任务；不替换原任务的结果接收者 |
| 投递结果 | 正在将已保存的结果发送到 QQ |
| 已完成、处理失败、已中断、已取消 | 查看“执行”和“投递”两列，判断具体完成或失败的环节 |
| 状态待确认 | 请求结果或投递结果尚不明确，先核对实际状态 |

执行状态与投递状态独立。例如模型执行完成后，QQ 可能显示“部分投递”或“投递状态待确认”；模型失败的错误说明即使已投递，执行结果仍是失败。长结果截断、部分消息被接受、附件转换失败、平台拒绝、请求超时和投递审计失败使用各自的受控诊断原因。

“已投递”表示平台接口已接受本次结果，不表示用户已阅读。状态不明确时不自动重发消息或启动同一任务；原完整结果仍按原有规则保存在消息历史中。

## 补充、停止与重启

同一合并批次的源消息共享任务编号。后续补充使用单独编号并关联主任务；主任务的执行和投递变化会传给已经接收的补充，准备失败或未被接收的补充不会被错误标成完成。界面显示关联的主任务短编号。

停止会取消尚未提交的输入；正在执行的任务仍等待模型确认中断。已知不同轮次或前一轮迟到的通知不能覆盖新任务。启动响应丢失后，只有匹配 thread/turn 的真实通知才能确认后续执行结果。

重启时，已配置账号中未结算的记录被标为待确认，不自动重跑、补发或恢复过期审批。仍已确认的执行结果保留；尚未确认的投递单独保留未知。这个过程记录恢复后的认知状态，不代表已重新调用模型核对。

## 诊断和隐私边界

诊断分别显示 QQ 连接、账号进程、任务记录采集及最近执行/投递状态。尚未为账号启动进程时显示“账号进程未启动”；进程或 HTTP 可用不会被当成模型调用可用。诊断接口不会为查状态而启动 Codex 或调用 QQ。

任务表与阶段事件保存在现有 `runtime/history.sqlite`，不改变原消息、记录数量和导出内容。升级前的消息没有完整阶段证据，因此不会回填假时间线。标题可能包含用户输入的短摘要，任务编号、源消息和时间线均属于账号私有数据。

阶段事件只接受受控状态、标签和原因，不复制模型全文、原始日志或配置凭据。查询须经过原有本机来源检查及登录验证，并明确指定已绑定账号；他人账号的任务与不存在的任务使用相同的 404 响应。任务详情仅显示最近 100 个阶段，任务列表默认读取最近 10 项。

采集失败会显示当前账号的记录缺口，不能据此认定任务没有执行。诊断记录故障不会自动重试或改变已经发出的模型、QQ 操作。

## 离线预览和验证

```powershell
npm run preview:tasks
```

脚本使用系统临时目录、两个演示账号和随机本机端口，只提供合成历史与任务界面；不读取生产配置，不连接 QQ 或 Codex，不支持修改和导出。打开命令输出的 URL，结束时输入 `quit` 或按 Ctrl+C，临时数据库随后清理。此预览用于界面验收，完整开发实例隔离仍按 [路线第二项](ROADMAP.md#2-独立开发模式与持续测试) 另行实施。

自动检查运行 `npm run check` 和 `npm test`。真实手机端 `/status` 排版与实际多账号、多模态组合仍在 [待办](BACKLOG.md) 中保留对应验收。
