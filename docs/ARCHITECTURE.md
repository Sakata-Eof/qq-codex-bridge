# 架构与设计约束

## 消息链路

QQ 官方网关 → `qq.mjs` 规范化事件 → `accounts.mjs` 校验配对账号并去重 → 对应账号的 `Bridge` → 独立 Codex App Server 进程 → 任务结果/审批/媒体 → 当前 QQ 会话。

`server.mjs` 负责组装实例并提供本机管理 API。`codex.mjs` 负责 JSON-RPC 传输；`bridge.mjs` 管理 thread/turn、忙碌状态、审批和结果投递。执行结束与 QQ 投递结束是不同阶段，投递尚未完成时仍需保持忙碌，防止新任务或模型切换打乱状态。

## 隔离与记忆

账号目录键由机器人 AppID 和 QQ 用户标识哈希派生。`runtime/users/<key>/` 保存该账号的会话状态、私有记忆、去重记录与 `codex-home/`；任务工作目录由账号配置限定，禁止重叠和目录越界。

账号首次创建时初始化专属 Codex 配置，登录资料仅在本机使用。已有会话迁移只匹配该账号已记录的 thread。全局记忆由管理页显式维护，私有记忆由各账号独立维护；会话轮换只携带本账号近期摘要及允许的记忆。

模型使用 Codex 原生上下文压缩；桥接还在配置的完成轮数或空闲阈值后，于下一次任务开始时换会话。新会话、上下文压缩和长期记忆是不同机制。实际轮换阈值以本机配置为准，文档中的默认值不能覆盖已保存设置。

## 历史为何单独存储

Codex 原始会话记录模型与工具执行过程。SQLite 记录 QQ 实际收发、附件、审批提示和错误，两者通过 thread ID 关联。Codex 生成了结果不能证明 QQ 投递成功，因此仍需桥接层审计。

`runtime/history.sqlite` 使用 WAL、账号/会话/时间索引、游标分页与 FTS5 trigram 搜索。旧 Codex 日志只从账号专属目录按变更导入，不在页面查询时重新扫描。短搜索词可能在会话范围内扫描，性能观察应区分数据库、HTTP、DOM 与媒体下载。

同账号、thread、源消息且正文相同的完整结果与成功投递可合并显示；数据库与导出保留两条原始事件。部分或截断发送保留完整结果并折叠，失败或未确认结果保持可见。附件首次点击后才加载，切换页面释放缓存。

## 浏览器和 QQ 控件

HTTP 仅绑定本机地址，管理 API 使用 Bearer 或签名 HttpOnly Cookie；浏览器登录采用 SameSite=Strict，并检查来源。不同浏览器分别登录。读取请求允许超时恢复，写入请求不得自动重放。

QQ 指令按钮使用消息型动作，复用账号授权与去重。审批凭证绑定账号、thread、turn 和请求，防止串号、过期及重复执行。面板和底部菜单仅同步本服务拥有的条目，保留其他自定义内容。

## 多模态与投递

图片转为模型输入；语音优先使用 QQ 转写，缺失时调用本地识别；视频由抽帧和音轨转写构成；文件保存在账号范围内。生成的文件经路径验证后回传，格式转换、文件大小和 QQ 回复次数均可能影响投递。不要通过自动重发掩盖不确定的发送结果。
